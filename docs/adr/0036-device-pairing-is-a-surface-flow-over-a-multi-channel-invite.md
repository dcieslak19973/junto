# Device pairing is a surface flow over a multi-channel invite

Status: accepted (Dan, 2026-08-21) — **implemented** · builds on [`0035`](0035-membership-is-set-based-except-after-revocation.md) · narrows [`0017`](0017-party-is-a-projection-membership-is-founder-granted.md)'s non-goal that web-surface member management stays out of scope — 0017's own founder-authorship rule for `MemberAdded` is untouched, only *which surface* may trigger it changes · cites [`0012`](0012-mcp-over-http-is-the-first-write-surface.md) (localhost posture), [`0021`](0021-member-codes-guard-agent-surfaces-only.md) (no member code on the human surface — though the per-endpoint gate varies; see Decision 4), [`0033`](0033-entries-are-signed-over-their-canonical-bytes.md) (canonical-byte signing; the byte-identity guarantee below), and the parallel rethink channel `3c38ead9-4907-4646-99b7-23b21933da35` (the transport-key request)

[`0035`](0035-membership-is-set-based-except-after-revocation.md) closed the key-transport gap: a member could enroll a second device's key without ever copying a private half across a wire. It shipped the mechanism with exactly one read surface (`junto keys list`) and no write surface at all, and its own non-goals deferred "device naming or a management UI beyond `junto keys list`" as "a later product question". That question comes due for a specific reason, not an abstract one: the primary human surface is the native one (Iced, [`0018`](0018-human-surface-is-a-desktop-shell-over-the-host.md)), and until this work it could not show a device even if it wanted to — there was no `/keys.json`, `unrecognized`/`unverified` badges rendered on the web surface only, and a revoked member's post-cutoff entries looked completely normal in the surface Dan actually uses. Meanwhile the ceremony itself did not scale: `keys::signing_key` mints one keypair per machine, reused across channels, but the keyring `0035` built is a **channel** projection and the invite envelope named exactly one channel — so publishing one machine key into N channels was N full exchanges, each burning its own 600-second fuse, against a machine registry already holding 14 channels. The [spec](../superpowers/specs/2026-08-21-device-pairing-surface-design.md) this ADR records is written against those three facts and the plan at the same path; read it for the seam-level detail this record does not repeat.

This ADR reopens exactly one thing `0017` said, and nothing else. `0017`'s non-goals named "**Web-surface member management** — the web surface stays verification-acts-only; granting membership is `junto add-member` (CLI plumbing, like `junto open`) or an MCP tool for founder-agents" — that is the boundary this work crosses: `POST /invites`, `POST /devices/enroll`, `POST /devices/preview`, and `POST /members` all live on the host's HTTP surface now (`crates/junto/src/web.rs`'s route table). `0017`'s actual rule — only the founder authors a `MemberAdded` — is untouched. `0021` still confines member-code checks to agent surfaces, but this slice does not prove that with one uniform mechanism: `/invites` and the retire/revoke pair gate through `identity::require_founder`; `/members` has no gate of its own at the HTTP layer — the founder check runs once per channel inside the redemption engine itself (`main.rs`'s `redeem_one_channel`, comparing the channel's own founder against the caller); and `/devices/enroll` — the one endpoint that may mint secret material — has **no founder check and no member code at all**: the invite token is the authorization (`invites::consume`'s downstream `WrongMember` check verifies it), and the caller being this machine's own localhost, never a network peer, stands in for one (`0012`). `0033` still signs every entry over its canonical bytes and still treats verification as a projection fact, never a gate. What is new is the shape of the envelope that carries an invite, and the fact that identity now has a write surface at all outside a terminal.

## Decision

**1. The invite envelope goes to v2 and carries a channel set.** `InvitePayload.channels: Vec<String>` replaces the single `channel: String` field — canonical ids, resolved before minting, capped at `MAX_INVITE_CHANNELS = 32`, required non-empty, each element bounded by the existing `MAX_FIELD_CHARS`. One redemption now grants every channel the founder ticked in a single pass, reporting a **per-channel outcome** (`granted` / `already_a_member` / `invite_already_used` / `not_founder` / `failed`). A channel refused *before* any attempt (`not_founder`, `already_a_member`) never touches the invite record and stays retryable. Every channel that reaches the append is consumed **first** (`main.rs`'s `redeem_one_channel`: "Burn the invite record BEFORE recording the member... this fails closed"), so a channel whose append then fails is already spent — and because `invites::channels_for` filters out every consumed record on every read, that channel simply drops out of the covered set on the next redemption attempt (`redeeming_a_mixed_set_burns_only_what_it_granted`, `a_failing_channel_reports_failed_and_the_run_keeps_going`); if it was the only channel still covered, redemption refuses the whole thing as exhausted rather than silently offering nothing. `invite_already_used` is reachable only from a stale duplicate invite record for the same `(token, channel)` — a second `issue` call landing on top of one already consumed — not from a normal re-paste after a partial failure. `PAYLOAD_VERSION` is `2`; a v1 code is refused outright with a message naming the fix ("mint a new one"), because the 600-second TTL leaves no in-flight window where a v1 code could still be live when v2 ships — there is nothing to shim.

**2. The channel set never travels in the code.** The founder's own `invites.toml` already holds one `InviteRecord` per `(token_sha256, channel)` — `issue` is called once per channel with the same token — so `invites::channels_for` recovers the covered set locally, by token hash, without the far side ever telling it. This is load-bearing for the founder's trust model: the redeem screen shows what a code is about to grant by asking the founder's own machine, not by trusting a list the joiner's machine could have altered in transit.

**3. A device now carries two keys, and the second is new.** `Member.transport_public_key` (`crates/junto-kernel/src/member.rs`) is `Option<PublicKey>` with `#[serde(skip_serializing_if = "Option::is_none", default)]` — the field that actually rides inside an entry's canonical bytes. `KeyGrant.transport_key` (`crates/junto-kernel/src/ledger.rs`) carries the same public half but is a **projection** type, folded at read time from `Member.transport_public_key`; it derives no `Serialize`/`Deserialize` at all, so the serde question does not arise for it — only `Member` ever touches the wire. This additive field is what makes the byte-identity claim hold: a `Member` written before this change carries no `transport_public_key` key in its JSON at all, so it deserializes and re-canonicalizes to exactly the bytes it always had, which is what keeps its signature valid — gated by `serial.rs`'s existing round-trip tests (`round_trips_every_payload_kind`, `golden_canonical_form_is_byte_stable`), neither touched by this work, plus a dedicated guard, `a_member_without_a_transport_key_serializes_exactly_as_before` (`crates/junto-kernel/src/member.rs`), whose own comment calls itself "the byte-identity guard for every entry ever written." The transport key is never a verification key: `project_unverified` and every signature check still resolve against `KeyGrant.key` alone; a transport-key signature is deliberately rejected (`an_entry_never_verifies_against_a_transport_key`, `crates/junto-kernel/src/ledger.rs`). This was requested mid-plan by the parallel *Multiplayer-first rethink 20260821* channel (`3c38ead9-4907-4646-99b7-23b21933da35`, diverged from `junto-dev`): its federation-topology decision has every member's own machine act as a host, addressed by federation transport (iroh) using an Ed25519 public key as the peer identifier for a QUIC/TLS handshake — and reusing the signing key for that handshake would violate the exact key-separation discipline `0033` exists to defend.

**4. The surface becomes an authorization site for identity, gated per endpoint — not by one uniform check.** `POST /invites` and the retire/revoke pair authorize through `identity::require_founder`, the same founder check the CLI's `revoke-member`/`retire-device` already used, now shared. `POST /members` carries no gate of its own at the HTTP layer; the founder check happens once per channel inside the redemption engine (`main.rs`'s `redeem_one_channel`, comparing the channel's own founder against the caller). `POST /devices/enroll` — the one endpoint that may create secret material — has **no founder check and no member code**: the invite token itself is the authorization, and the caller being this machine's own localhost, never a network peer, is what stands in for one; it mints only for the email its decoded invite carries (never a request-supplied override) and is never exposed on the mobile/remote read-only web role. `POST /devices/preview` and `GET /channels/{c}/keys.json` are unauthenticated reads — a preview appends and consumes nothing, and a keyring listing publishes only fingerprints (Decision 5). None of this asks a human for a member code, honoring [`0021`](0021-member-codes-guard-agent-surfaces-only.md)'s principle that codes guard agent surfaces only — but through several different mechanisms, not the single `WriteAuth::Human` enum diverge/converge already uses.

**5. `keys.json` publishes fingerprints only** — 16 hex characters, the same helper the CLI's `keys list` already used — never a full public key, for the same reason `0035` gave for the CLI: a shared terminal (or, now, a shared screen) is not the place for a full key to sit in scrollback.

**6. Codes still travel by paste.** OS deep links (`junto://`) would halve the steps, but scheme registration is installer work with no distribution story yet to register a handler from (parked `779ad00e`); paste stays the trust anchor on both ends, as the enrollment design's non-goals already said.

## Considered and rejected

**Device-level trust valid everywhere**, instead of a per-channel grant multiplied by a channel set. This is the more elegant model on paper — enroll a device once, it is trusted across every channel its owner joins, no N-per-channel bookkeeping ever. It loses because junto has no cross-channel identity concept to hang that trust on: a `KeyGrant` is an entry in one channel's own ledger, and a grant is only as trustworthy as the founder who authored it for *that* channel. Device-level trust would mean one stolen device reaching every channel its owner was ever added to, including ones the founder who enrolled it never considered and would not have approved. The channel set stays a set the founder ticks, not a property of the device.

**Host-to-host enrollment**, where the joining machine's host talks directly to the founder's host over the network instead of a human pasting two codes. Fewest steps of any option on the table — no copy, no paste, no out-of-band confirmation at all. It loses for exactly the reason it looks attractive: it dissolves the trust bootstrap the invite token exists to provide. The founder's host would have to accept a write from an unauthenticated remote peer, which is precisely the posture [`0012`](0012-mcp-over-http-is-the-first-write-surface.md) rejected for the write surface generally — localhost-only, no network-reachable write path with no auth in front of it.

**Echoing the channel set back in the enroll payload**, so the joiner's code names the channels rather than the founder's own store recovering them. Its real case is robustness, not mere cheapness: `invites::channels_for` reads `<junto-home>/invites.toml` and nothing else, so rejecting the echo makes redemption structurally dependent on one machine's local file — an enroll code is redeemable only on the founder machine that minted it, only while that record survives `prune` and its own expiry. Echoing the set would have made the code self-describing and redeemable from wherever the founder happened to be — a genuine cost this decision accepts, not a phantom one. It still loses on trust direction: echoing puts the founder's own channel names into a code that crosses machines and asks the founder to trust a list the far side produced, when the founder's own store already holds the authoritative answer, recoverable by the token hash the founder minted in the first place. Decision 2 above is what results from rejecting this.

**Accepting v1 invite codes alongside v2**, to give any code minted just before the upgrade a grace window. It loses because there is no window to grace: an invite's TTL is 600 seconds, so no v1 code outlives a release by the time v2 code is running on both ends. A shim here would be scaffolding for a race condition that provably cannot occur.

## Consequences

- **Party membership and signing authority now diverge visibly, not just in projection.** `0035` already made this true in the data model; this ADR makes it true on screen — the members panel shows a person with zero active grants as exactly that, admitted but unable to write, which will read oddly the first time someone sees it and is nonetheless the honest account.
- **A lost laptop is still N retirements across N channels.** One pass grants many channels; it does not collapse retirement the same way. Losing a device enrolled into fourteen channels still means fourteen `retire-device` (or `revoke-member`) acts, one ledger per channel, because retirement parks a grant in that channel's own ledger and there is no cross-channel act to park it everywhere at once. This is named, not fixed — the rejected device-level-trust option above is what would fix it, and it was rejected for good reason at today's scale.
- **The 32-channel cap and the per-channel walk are sized for today, not for tomorrow's shape.** The channel registry backing this design holds 14 channels; the cap and the outcome-per-channel walk are comfortable there. The parallel rethink channel's provisional collapse decision — the channel/thread primitive becoming cheap enough that N goes to hundreds — would strain both: a founder ticking hundreds of channel checkboxes per invite is not a UI, and a per-channel walk over hundreds of entries is not free. Nothing here forecloses a future device-level or grant-all redemption path; `channels_for`'s contract ("which channels does this token still cover") and the per-channel outcome walk are deliberately factored so a future source of that set can replace today's `invites.toml` recovery without a third envelope version. That day has not arrived, and this ADR does not pretend it has.
- **The CLI keeps its agent-facing role, but loses a flag.** `junto invite --member <email> --channel <c>` is now repeatable, each resolved to a canonical id before the token is minted; `junto add-member --enroll <url> --kind <k>` **no longer accepts `--channel`** at all — the channel set comes from `channels_for`, strictly better than a human retyping one name on the machine that already knows the answer. Any script or memory of the old flag now fails fast rather than silently addressing the wrong channel.
- **`unverified` becomes visible natively, closing a real gap `0035` left open.** `EntryDto` now carries `unverified` alongside `unrecognized`, and the native timeline renders both — so `0035`'s revocation cutoff stops being a fact that only ever showed up in projection tests or the web surface nobody at Dan's desk actually opens.
- **The GUI side of this is verified by pure-function tests, not a widget harness — `junto-iced` has none.** Every pure helper introduced for the surface (countdown formatting, device/member summary lines, the invite-tick liveness predicate) is unit-tested; the update-loop wiring (double-submit guards, form-close cleanup, refetch chaining) and every visual claim — the countdown actually ticking on screen, the redeem preview rendering before a kind is picked, the badges' color and suppression rules, a host failure surfacing as a visible error line rather than a blank roster — are enumerated as a live-GUI-run checklist in the implementation report rather than asserted here. **That live run had not happened as of this record**; treat any claim about on-screen behavior beyond what a pure-function test pins as pending, not verified.
