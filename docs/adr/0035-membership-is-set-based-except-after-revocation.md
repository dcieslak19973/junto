# Membership is set-based, except after revocation

Status: accepted (Dan, 2026-08-21) — **implemented** · builds on [`0017`](0017-party-is-a-projection-membership-is-founder-granted.md), [`0033`](0033-entries-are-signed-over-their-canonical-bytes.md) · amends [`0017`](0017-party-is-a-projection-membership-is-founder-granted.md)'s non-temporal membership check, for revoked members only · addresses limitation 1 ("no key transport for a remote watcher") recorded in [`0034`](0034-crdt-confined-to-the-live-plane.md)

[`0017`](0017-party-is-a-projection-membership-is-founder-granted.md) made Party membership **set-based and non-temporal** on purpose: an entry counts iff its author is in the Party, wherever the granting `MemberAdded` falls in canonical order relative to the entry — deliberately, to avoid clock-skew landmines and to not orphan pre-Party entries. [`0033`](0033-entries-are-signed-over-their-canonical-bytes.md) then made authorship verification a **projection fact, never a gate**: an entry whose signature does not verify against the author's keyed public key still projects, merely flagged `unverified` (`ChannelView::unverified`, `crates/junto-kernel/src/ledger.rs`). Put those two together and a member whose every key is compromised or abandoned still has their later entries **recognized** — carrying standings, closing gates, appearing in Sessions and lineage — merely flagged `unverified`. Offboarding had no mechanism: nothing a founder could do would stop a departed member's future entries from counting.

The device-key-enrollment work ([spec](../superpowers/specs/2026-08-21-device-key-enrollment-design.md), [plan](../superpowers/plans/2026-08-21-device-key-enrollment.md)) that closes [`0034`](0034-crdt-confined-to-the-live-plane.md)'s key-transport gap — a member could only ever hold one signing key, minted on whichever machine happened to grant their membership, so a second device had no way to get a key of its own without copying secret material by hand — forced this question open at the same time: multiple devices per member means multiple *grants* per member, and multiple grants per member means "revoke this person" can no longer mean "delete the one key," because there may be several.

## Decision — a per-device keyring, founder-authored retirement, and enrollment that never moves a secret

**Membership stays set-based for every member who has not been revoked.** Nothing here reopens `0017`'s core argument. What changes is that a member's authority to sign is now derived from a **per-device projection distinct from the Party**, and losing every device on that projection now has a real, temporal consequence.

- **`KeyGrant` and the `Keyring`** (`crates/junto-kernel/src/ledger.rs`). `KeyGrant { key, granted_by, retired_at }` is one key ever granted signing authority for an email — `granted_by` is the `ChannelOpened` genesis or `MemberAdded` entry that authorized it, `retired_at` is `None` until parked. `Keyring = HashMap<String, Vec<KeyGrant>>` answers "which keys may sign for this email", deliberately distinct from `Member`/`Party`, which answer "who is on the roster": a member has exactly one roster row but can hold many grants, one per device. Only the canonically first `ChannelOpened` grants the founder's key, and a `MemberAdded` grants only when authored by the founder — the same hard first-genesis/founder-only rule `project_party` already enforces for roster admission, so a stray peer cannot inject a signing key for an arbitrary email by appending its own genesis or member-added entry.
- **Device enrollment is a three-step exchange, and no secret ever crosses a wire.** `junto invite --member <email> --channel <channel>` (founder-only; the channel argument is resolved to its **canonical id** before the invite token is minted, so a name typed one way at `invite` and another at `add-member --enroll` cannot silently address two different channels) issues a short-lived, single-use token. `junto enroll --invite <url>` runs **on the new device**: it mints that device's own keypair locally (`keys::signing_key`) and echoes back an enroll payload carrying only the **public** half. `junto add-member --enroll <enroll-url> --channel <channel>` (founder-only, run back on the founder's machine) burns the invite token (`invites::consume`) and appends the `MemberAdded` that grants the key the enrolling device minted for itself — the founder never sees, generates, or transmits the device's private key.
- **`Host::add_member` (`crates/junto/src/host.rs`) no longer mints a keypair on behalf of a supplied identity.** When no key is supplied and no key already exists locally for that email, it refuses outright for a human member (`member.kind == MemberKind::Human`) — minting a human's key on the founder's machine instead of their own is exactly the bug this plan exists to close — while an agent, which runs on this machine by construction, may still mint fresh. Re-granting an email already on the roster is a no-op on the Party (first-write-wins by email) but **not** necessarily on the keyring: it appends a new `MemberAdded`/grant whenever the supplied key is genuinely new to that email's keyring, and — deliberately — a previously **retired** key is re-grantable, because `keys::signing_key` mints a device's keypair once and remembers it forever; without allowing a retired key back in, there would be no path back for a member who was revoked and then legitimately re-admitted on the same device.
- **`--kind` is now required on the keyless `add-member` path, and conflicts with `--enroll`.** That flag decides whether this machine may mint someone else's key, so it can no longer be silently defaulted — a deliberate CLI break. On the `--enroll` path the enrollment act itself already establishes kind, so re-typing it would risk divergence from what was actually enrolled.
- **Retirement reuses the existing `Park` entry kind — no new entry kind is introduced.** A founder-authored `Park` whose `target` names a grant's `granted_by` retires that grant as of the park's own `timestamp`. Verification then treats that grant as active for any entry stamped **at or before** the park's timestamp — the boundary is inclusive (`KeyGrant::active_at`) — and inactive only for entries stamped strictly after. A `Park` authored by anyone but the founder never reaches the retirement map at all (the same load-bearing founder-only guard `project_keyring` applies elsewhere); one authored by the founder but targeting an entry that granted no key is ignored by the same dangling-target leniency the rest of this file already extends. **When two founder-authored `Park`s target the same grant, the *earliest* wins** — a grant's retirement can only move earlier, never later, regardless of append order — so a founder cannot un-retire a device by parking it again later with a different timestamp.
- **The revocation cutoff is a distinct, email-level rule from the grant-level retirement above, and the two must not be blurred.** An email acquires a cutoff only when **every** one of its grants is retired; while even one grant is still active, there is no cutoff at all, because partial retirement (one lost device among several) must not offboard the person. When a cutoff exists, it is the ***latest*** `retired_at` among that email's grants — the moment it held no valid key at all, across every device — never the earliest. An entry from a cutoff email is `unrecognized` iff its timestamp is strictly after the cutoff; stamped at or before, it still counts. **This rule was drafted first as the earliest retirement and corrected mid-plan (Task 9c):** an earliest-wins cutoff would let a member's very first device retirement reach back and retroactively unrecognize real work they went on to write from a second, still-active device, the moment that second device was *eventually* also retired — punishing a legitimate T1..T2 span for an unrelated later event, not for anything wrong with the work itself. The member is **never removed from `ChannelView::party`** by any of this — doing so would mark every entry that author ever wrote as unrecognized and erase their history from every downstream projection, which was considered and rejected (see below).
- **Operator surface:** `junto keys list --channel <channel>` (per grant: member, a 16-hex key fingerprint — never the full public key on a shared terminal — the granting entry id, and its retirement timestamp when set), `junto revoke-member --member <email> --channel <channel> --rationale <why>` (one founder-authored `Park` for every currently active grant that email holds — the person stays in the Party, only their post-now entries stop counting), and `junto retire-device --grant <entry-id> --channel <channel> --rationale <why>` (park exactly the one grant the id names). `--channel` and `--rationale` have no defaults on the last two; both are required.
- **The live plane** (`crates/junto/src/live_ws.rs`) authenticates a watcher's WebSocket handshake against the keyring's **active** grants for the claimed email, and — the diagnosis this handshake exists to give — classifies a failed verification into one of three genuinely different causes rather than one bare "does not verify": `NotAMember` (the email never joined at all), `Unenrolled` (a member, but no device of theirs is on file, or the device that just tried is not one of them), and `Revoked` (every grant that email ever held is retired). Only `Unenrolled`'s message points the caller at `junto enroll`; telling a revoked member to enroll would be wrong and cruel. The three-way distinction leaks nothing a caller could not already learn some other way: the same unauthenticated router this socket is mounted on already renders every party member's email, unauthenticated, into the channel page's member chips (`GET /channels/{channel}` → `channel_page`, `crates/junto/src/web.rs`; the email lands in the chip's `title` attribute, `crate::render`), so the three-way distinction tells a caller nothing about this channel's membership they could not already read from that page.

## Considered and rejected

- **Removing a revoked member from the Party projection**, instead of layering a keyring-derived cutoff beside it. Rejected: the Party gates every fold in this codebase (standings, gate status, sessions, lineage) by "is the author in the Party" ([`0017`](0017-party-is-a-projection-membership-is-founder-granted.md)), so removing a row would not just stop *future* entries counting — it would flip *every entry that member ever authored*, including work written while they were in good standing, to unrecognized. That erases history the record exists to keep; a revoked member remains visible with their history intact, which is the honest account of what happened.
- **A new entry kind for retirement** (something like `KeyRetired`), instead of reusing `Park`. Rejected: a founder setting aside a device's authority is exactly what `Park` already means for any other subject ([`0003`](0003-ledger-entry-content-model.md)'s closed kind set), and the entry needs nothing `Park`'s `{ target, rationale }` shape does not already carry. No new kind, no migration, no second code path for the same idea.
- **The cutoff as the earliest retirement across an email's grants.** Drafted first, shipped in Task 3, and corrected in Task 9c once its consequence was traced through: it answers "when did this person first lose *a* device" rather than "when did this person lose *every* device", and the two questions diverge exactly in the window between a lost device and a person's actual departure — the span this ADR's cutoff rule now protects.

## Amendment to ADR 0017

[`0017`](0017-party-is-a-projection-membership-is-founder-granted.md) states plainly: *"The membership check is set-based, not temporal: an entry counts iff its author is in the Party, regardless of where the membership grant falls in canonical order relative to the entry."* This ADR amends that statement — **for revoked members only**. For every member who has never had every one of their key grants retired, `0017`'s rule is exactly as written and completely unchanged: set-based, non-temporal, no cutoff, no exception. `0017`'s own reasoning against a temporal check (clock-skew landmines, orphaning pre-Party entries) was about **admission**, not revocation, and remains correct there; this ADR does not relitigate it. Recognition as a whole, though, is no longer purely set-based — Party membership now answers "was this email ever admitted", not "may this email's entries count right now" — and any code or reader that treated those two questions as one and the same needs to be checked against the other. `ledger.rs`'s comment claiming a purely set-based check has been corrected to name this exception in place (`project_unrecognized`'s doc comment).

This repo's precedent for a later ADR narrowing an earlier one without rewriting it is [`0014`](0014-channel-identity-is-minted-names-are-substrate-scoped-labels.md) superseding `0012`'s UUIDv5 named-channel clause: the superseding ADR's status line names exactly what it changes, the index (`README.md`) annotates the older ADR's row with a forward pointer, and the older ADR's own body is left standing untouched, because the limitation or rule it recorded was correct when it was written and the record does not rewrite history to pretend otherwise. This ADR follows that same shape: the status line above names the amendment and its scope, and `0017`'s file is left unedited — a reader arriving there directly sees the original, correct-for-its-time rule exactly as written, with no forward reference inside it. The pointer instead lives where the precedent puts it: `README.md`'s index row for `0017` now reads forward to this ADR, so a reader who arrives via the index sees the amendment before they ever open `0017` itself.

## Consequences

- **Recognition is no longer purely set-based.** It is set-based for every never-revoked member and temporal, past a cutoff, for a revoked one. Any future surface that folds over "is this author in the Party" needs to also ask "and are they still recognized as of this entry's timestamp" if it means to honor revocation.
- **A revoked member remains visible in the record with their history intact.** Nothing about this design deletes, hides, or retroactively distrusts anything they signed while any one of their devices was still active.
- **[`0034`](0034-crdt-confined-to-the-live-plane.md)'s limitation 1 is now addressed**, not merely revisited: a member enrolls a second device's key without ever copying private key material between machines, and the live plane's watcher handshake authenticates against that device's own grant. `0034`'s own text is left standing (the gap was real when it was recorded); this ADR and the [spec](../superpowers/specs/2026-08-21-device-key-enrollment-design.md) are the resolution.
- **Retroactive distrust of a compromised key remains explicitly out of scope.** If a device's key is stolen rather than merely lost, retiring that one grant does not touch, flag, or re-examine anything already signed by it before the retirement, nor does it narrow the window to just that device's own signatures the way a genuine compromise response would need to. That is a different decision, not made here.
- **`--kind` now required on the keyless `add-member` path is a deliberate CLI break.** Existing scripts that omitted it, relying on a default, now fail fast with an actionable error rather than silently minting a key of the wrong authority on the wrong machine.
