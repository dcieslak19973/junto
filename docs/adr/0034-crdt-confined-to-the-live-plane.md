# CRDT is confined to the ephemeral live plane; the durable record stays CRDT-free

Status: accepted (Dan, 2026-08-20) — **implemented** · builds on [`0011`](0011-sync-is-push-fetch-plus-convergent-union-merge.md), [`0033`](0033-entries-are-signed-over-their-canonical-bytes.md)

junto's hard constraint #3 (`CLAUDE.md`) reads: *"Durable record = git refs… Append-only; **no CRDT** — concurrent writes interleave by `(ts, author)`."* [`0011`](0011-sync-is-push-fetch-plus-convergent-union-merge.md) is the argument behind that line, and it is narrower than the constraint's wording suggests: entries are immutable and identified by id, so at sync time *set union is the entire merge* — there is nothing to diff, no conflict to resolve, no CRDT machinery with a job to do. The argument is about the **durable record** specifically. It says nothing about state that isn't durable and isn't record.

Zed's Delta/DeltaDB (assessed in [`competitive-landscape.md`](../competitive-landscape.md) §"Zed — Delta & DeltaDB") tested that boundary. DeltaDB CRDT-replicates a conversation and worktree together in real time so anyone can join a session mid-flight, comment anywhere, and watch references survive as code moves — a capability junto's original diagnosis (alignment is async/social, not co-presence) had dismissed as non-essential. Dan reopened the question 2026-08-20 (§"The reopening"), and the design work that followed ([`docs/superpowers/specs/2026-08-20-live-session-plane-design.md`](../superpowers/specs/2026-08-20-live-session-plane-design.md), executed by [`docs/superpowers/plans/2026-08-20-live-session-plane.md`](../superpowers/plans/2026-08-20-live-session-plane.md)) is that design's own dead-ends entry: *"this design requires an ADR scoping [hard constraint #3] to the durable record."* This is that ADR.

## Decision — scope the constraint to the record; permit CRDT in a separate live plane

**The "no CRDT" constraint governs the durable record — `refs/junto/*`, `LedgerEntry`, the union-merge sync path — and nothing else.** It is not relaxed there; ADR 0011 is untouched, and no entry kind, fold rule, or sync mechanism changed to ship this design. What changes is that a **second, ephemeral plane** now exists beside the record, and CRDT is permitted inside it:

- **`LiveDoc`** (`junto-live`, a new crate that owns the loro dependency) — one [loro](https://github.com/loro-dev/loro) document per live Session, never synced through `refs/junto/*`, never itself a ledger entry. Three containers, two write policies:
  - `conversation` and `worktree` are driver-only `LoroMovableList`s using seq-keyed replace-in-place (the session's live event stream and derived edit/diff *events* — not replicated file content) — single-writer *by policy*, not by the data model, so lifting it later (ladder rung 3) is an authorization change, not a rewrite.
  - `annotations` is a multi-actor add-only `LoroMap` keyed by annotation id, holding canonical-JSON `Annotation` strings — the one container any authenticated watcher may write into.
- **`Presence`** is deliberately kept outside `LiveDoc`, riding loro's own, separate `EphemeralStore` (30s timeout) on its own sync channel — transient watcher membership has no place in what gets archived as a permanent snapshot; never persisted, never archived.
- **Anchors and annotations live in `junto-kernel`, signed like entries.** `Anchor::{Code, Stream}` — `CodeAnchor { commit, path, blob, span }` pins "what it was" at a commit; `StreamAnchor { session, op_id }` pins a position in the live stream, needing no re-anchoring because CRDT op ids are stable by construction. `Annotation` is signed over its own canonical bytes exactly as an entry is ([`0033`](0033-entries-are-signed-over-their-canonical-bytes.md)'s pattern reused, not re-invented) via `SigningKey::sign_bytes`/`PublicKey::verify_bytes`. `CodeAnchor` re-anchoring (`Exact | Moved | Orphaned`, degrading honestly when content moves or disappears) lives in `junto-substrate-git`, shelling out to git diff plumbing the same way the rest of that crate does.
- **Transport is one authenticated WebSocket per session**, `GET /channels/{channel}/sessions/{session}/live` on the driver's own host — an ed25519 challenge-response against the channel's existing keyring, signing the handshake nonce's ASCII bytes verbatim. `validate_annotation_update` is the write-side gate, checked on every incoming frame as a unit: an unrecognized sender, a frame that touches a driver-only container, a frame that mutates an existing annotation's stored content, or a new annotation that fails any of its five checks (parses, its `id` matches the map key it's stored under, its author matches the sender, it is signed, and the signature verifies) rejects the **whole frame** — there is no partial merge. The sender gets a `Frame::Rejected { reason }` back over the same socket; nothing invalid is ever merged into the doc.
- **Watcher annotations reach the driving agent through the existing steer machinery**, not a new capability: `live_bridge` batches pending annotations and delivers them via the mid-turn-steer control channel ([`0032`](0032-mid-turn-steer.md)) at the next turn boundary, or immediately on the urgent flag.
- **Durable outcomes still fold into entries through existing verification acts, and only those.** At session (turn) end the `LiveDoc` snapshot is archived as a signed artifact — `turn-{n}-live.loro`, or `live-{id}.loro` for an unattributed end — the same artifact-attachment path every other session output already uses. The live plane produces no new entry kind; nothing it holds is durable until a human or a verification act says so through the record's normal path.

Both anchor kinds do double duty: `CodeAnchor` plus re-anchoring is exactly what the "decision blame" projection (code/line → entries + Sessions, `competitive-landscape.md`'s strongest borrow from Delta — deferred, not parked; still on the roadmap) needs, and that projection is a later read over the same type — built once, here, without a second implementation.

## Consequences

- **Rung 3 of the reopening's ladder** (a shared, multi-writer plan/conversation document) becomes an **authorization change against a representation already built to hold it**, not a rewrite — `LiveDoc`'s driver-only write policy on `conversation`/`worktree` is enforced by session ownership, not by the CRDT's structure. **Rung 4 (replicated worktrees) is not**: `worktree` holds derived edit/diff events, not replicated file content, so nothing here is already built to hold it — climbing rung 4 stays a new substrate plane (`competitive-landscape.md`), not a policy flip. Whether to climb either rung is still an open, separate decision; nothing here pre-approves it.
- **Any future CRDT use outside a live plane or a versioned, archived artifact requires a new ADR.** This one licenses exactly the shape built: per-session, non-durable, archived-on-end. A CRDT that touched `refs/junto/*` directly, or that outlived a session without folding through a verification act, would be a different decision.
- **A second data model now exists in the codebase.** `junto-kernel`'s entries and `junto-live`'s loro document do not share a merge strategy, a persistence path, or a mutability story, and a contributor has to know which plane they're in. The seam is deliberately a crate boundary (`junto-live` alone depends on loro) so a swap — or a rollback — stays one crate wide.
- **A new dependency, with transitives worth naming rather than glossing over.** loro is MIT. It pulls in `im`, `sized-chunks`, and `bitmaps` — all MPL-2.0 — as transitive dependencies; MPL-2.0 is file-level copyleft and does not touch hard constraint #1 (no *source* copyleft, linking permitted), but it is a license family junto had none of before this crate, accepted here by explicit decision rather than by not looking.
- **One more surface to keep secure.** `validate_annotation_update` is now the boundary between "any authenticated watcher can write" and "the driving agent reads it as trusted steering context." A gap there is a prompt-injection path into a running Session, not just a data-integrity bug.
- **Two known gaps, carried forward rather than hidden:**
  - Comments on an autonomous Outcome-loop Session **queue but do not deliver**. Those turns run without a real control-channel reader by design; every `flush_pending` attempt drains the queue and immediately re-delivers into `NotLive`, so it requeues instead of reaching the agent, until a human steers that Session from the web UI onto the steerable path. Documented at the fix site (`crates/junto/src/live_bridge.rs`, `flush_pending`'s doc comment) as an accepted trade-off: the alternative — a control sender nothing reads — would make `steer_live` fake-succeed and write a false ledger note, which is worse than an honest queue that doesn't drain.
  - `junto-iced`'s WebSocket client uses `webpki-roots` (publicly trusted CAs). A self-hosted junto host behind a private or corporate CA fails the `wss://` handshake; a publicly-rooted TLS-terminating front (a standard reverse proxy) works. No client-side CA override ships in this design.

## Prior art (clean-room inspiration only)

Delta/DeltaDB is the competitive stimulus for this design's rungs 1–2 (join mid-flight, span-anchored comments), not its blueprint: its CRDT-replicated worktree and conversation-as-source-of-record are explicitly not cloned (`competitive-landscape.md` §"Concepts to borrow", *"Don't clone the CRDT worktree or conversation-as-source"*) — the engineering is enormous, DeltaDB is proprietary, and junto's record philosophy (state-not-history, provenance-bound, gated) is opposed to conversation-as-artifact. loro is a general-purpose Rust CRDT library evaluated and adopted on its own terms (MIT, `EphemeralStore` for presence, `LoroMovableList`/`LoroMap` fit the driver-only/multi-actor split), not a port of DeltaDB's internals.
